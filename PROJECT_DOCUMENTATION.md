# DevSecOps Pipeline: Project Architecture & Operational Guide

This document provides a comprehensive architectural breakdown and operational guide for the production-ready, security-hardened Python Flask web application.

## 1. Application Overview

*Note: While the request mentioned `src/` and `package.json`, this project is built using Python (Flask) as specified in the original requirements, utilizing an `app/` directory and `requirements.txt`.*

### Tech Stack
- **Framework:** Python Flask
- **Server:** Gunicorn (WSGI HTTP server for production)
- **Testing:** Pytest
- **Linting & Security Analysis:** Flake8, Bandit

### Key Components & Endpoints (`app/main.py`)
- **`GET /`**: Home endpoint returning a welcome message.
- **`GET /health`**: Health check endpoint used by the Application Load Balancer to verify service availability.
- **`GET /api/v1/status`**: Detailed status endpoint returning service metadata and the current running environment.

### Dependencies (`requirements.txt`)
- `Flask`: The core web framework.
- `gunicorn`: Production web server.
- `pytest`: For running the automated test suite.
- `flake8`: For code linting and style checking.
- `bandit`: For Python static application security testing (SAST).

## 2. How to Run & View the Application Locally

You can run the application locally using either native Python or Docker.

### Option A: Using Python directly

1. **Install dependencies:**
   ```bash
   python -m venv venv
   source venv/bin/activate  # Windows: venv\Scripts\activate
   pip install -r requirements.txt
   ```
2. **Run the application:**
   ```bash
   python app/main.py
   ```
3. **Preview:** Open your browser and navigate to http://localhost:5000. You can test the endpoints at http://localhost:5000/health and http://localhost:5000/api/v1/status.

### Option B: Using Docker

1. **Build the image:**
   ```bash
   docker build -t flask-devsecops-app .
   ```
2. **Run the container:**
   ```bash
   docker run -p 5000:5000 flask-devsecops-app
   ```
3. **Preview:** Navigate to http://localhost:5000 in your browser.

## 3. Complete DevSecOps Pipeline Architecture

The `.github/workflows/devsecops-pipeline.yml` workflow enforces security throughout the Software Development Life Cycle (SDLC) via 6 distinct stages:

1. **Code Setup & Tests:**
   - The code is checked out and Python is set up.
   - Dependencies are installed.
   - Code is linted using `flake8` to enforce style and catch basic errors.
   - The test suite is executed using `pytest`.

2. **Vulnerability & Secret Scan (SAST & Trivy FS):**
   - **Bandit** scans the Python source code specifically for common security issues (Python SAST).
   - **Trivy File System (FS) scan** checks the repository for accidentally committed secrets and known vulnerabilities in the OS packages and application dependencies.

3. **SAST (CodeQL Analysis):**
   - GitHub's native **CodeQL** engine performs deep static analysis of the Python code to find semantic security flaws and logic errors.

4. **Docker Build:**
   - The security-hardened, multi-stage Docker image is built.
   - Instead of immediately pushing it to a registry, the image is exported using `docker save` as a `.tar` artifact. This ensures the exact built image is the one scanned in later steps.

5. **IaC Scan (Terraform / Trivy Config):**
   - **Trivy Config scan** analyzes the Terraform code in the `./infra` directory. It flags misconfigurations, such as overly permissive security groups or unencrypted storage, before any infrastructure is provisioned.

6. **Container Scan & SBOM Generation:**
   - The Docker image `.tar` artifact is loaded.
   - **Trivy Image Scan** checks the built image for known CVEs. The results are generated in SARIF format and uploaded to GitHub.
   - A **CycloneDX SBOM (Software Bill of Materials)** is generated, detailing every component inside the container.

### Viewing Security Findings in GitHub
- **Security Findings:** SARIF reports generated by Trivy and CodeQL are automatically uploaded and can be viewed under the **Security tab -> Code scanning alerts** in your GitHub repository.
- **SBOM Artifact:** The CycloneDX SBOM (`bom.json`) is attached to the workflow run and can be downloaded from the **Summary page** of the specific Action run under the "Artifacts" section.

## 4. Infrastructure & Deployment Setup

The `./infra` directory contains modular Terraform code to provision a highly available and secure environment in AWS:

### Architecture Components
- **Amazon ECR (Elastic Container Registry):** Provides a secure registry for storing the application's Docker images. Push-based scanning is enabled.
- **Amazon ECS Fargate:** A serverless compute engine for containers. It runs the Docker containers without the need to manage underlying EC2 instances.
- **ECS Task Definition & Service:** Defines how the Docker container runs (CPU, memory, environment variables, IAM roles). The Service ensures that the desired number of tasks (e.g., 2 instances) are always running and registers them with the Load Balancer.
- **Application Load Balancer (ALB):** Distributes incoming HTTP/HTTPS traffic across the running ECS tasks in multiple Availability Zones.
- **Security Groups:** 
  - *ALB Security Group:* Allows inbound HTTP traffic (port 80/443) from the internet.
  - *ECS Security Group:* Strictly restricts inbound traffic so it only accepts connections from the ALB on port 5000, enforcing least-privilege networking.

### Deployment Workflow
When you are ready to deploy to the cloud, the following commands initialize the Terraform environment, preview the changes, and provision the resources on AWS:
```bash
cd infra
terraform init
terraform plan
terraform apply
```
